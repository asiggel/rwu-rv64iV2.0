\chapter{Test and Debug}

\section{Simulation Test Suite}
\label{sec:simtest01}

The \texttt{RV\_NoPipeline} and \texttt{RV\_PipelineCacheFwd} projects include a
regression test suite driven by CMake.
Each test assembles a dedicated firmware program, runs it under xsim, and checks
the result via GPIO output (0x55\,=\,pass, 0xFF\,=\,fail) or a waveform monitor.

\subsection{UART0 Simulation Tests}
\label{subsec:uartsimtest}

Two system-level tests verify UART0 end-to-end.
Firmware uses \texttt{CLKDIV\,=\,4}, giving a bit period of
$16 \times 4 \times 800\,\text{ns} = 51\,200\,\text{ns}$ at the 1.25\,MHz core clock.

\paragraph{uart\_tx}
Firmware writes twelve ASCII bytes (\textit{``Hello Rocker''}) to the UART TX FIFO
one by one, polling STATUS[0] (tx\_busy) before each write.
The testbench monitors \texttt{uart0\_tx\_o} and decodes each 8N1 frame,
comparing against the expected string.
On success GPIO\,=\,0x55 is written.

\paragraph{uart\_rx}
The testbench injects a pre-built 8N1 serial stream
(\textit{``We will rock you.''}, 17\,bytes) onto \texttt{uart0\_rx\_i}.
Firmware polls FIFOSTAT[21] (rx\_empty) until cleared, then reads the DATA
register; each received byte is compared against the expected ASCII value.
On full match GPIO\,=\,0x55; on any mismatch GPIO\,=\,0xFF.

\subsubsection{RX FIFO Pop Bug (Fixed 2026-06-05)}
\label{subsubsec:rxfifobug}

During development, UART RX reads returned 0x00 for every received byte.
Root cause: the non-pipelined CPU (\texttt{as\_cpux}) uses a two-cycle load
sequence --- EXEC\_ST (address and read-enable asserted) followed by EXECLD\_ST
(data captured by the register file).
The Wishbone master (\texttt{asMBpi}) holds STB\,=\,CYC\,=\,1 throughout both
cycles, so the UART slave's \texttt{rd\_data\_s} signal was high during EXEC\_ST,
popping the show-ahead RX FIFO at the EXEC$\to$EXECLD clock edge.
EXECLD\_ST then saw an empty FIFO and captured 0x00.

Fix: a one-cycle delay register \texttt{rd\_data\_r} was added in
\texttt{ip\_uart\_v2/src/as\_uart\_top.sv} and used as the FIFO \texttt{rd\_en\_i}.
The pop now fires at EXECLD$\to$FETCH0, leaving the FIFO head valid throughout
EXECLD\_ST.
The same pattern must be applied to any future read-once (clear-on-read) register
on this Wishbone bus.

\subsection{\texttt{RV\_PipelineCacheFwd} Simulation Tests}
\label{subsec:pipecachefwdsimtest}

In addition to the shared instruction-set regression (58 tests common with
\texttt{RV\_NoPipeline}, plus \texttt{ecall}/\texttt{ebreak} and the hazard
suite of Section~\ref{subsubsec:hazardTestSuite}, all run under xsim),
\texttt{RV\_PipelineCacheFwd} has test infrastructure the flat-SRAM
\texttt{RV\_NoPipeline} variant has no equivalent of, since it alone has a
cache/AXI4/QSPI-Flash memory subsystem:

\begin{itemize}
  \item \textbf{Cache-specific xsim tests:} \texttt{scratchpad\_intensive}
    (RMW byte/halfword/word isolation on the scratchpad SRAM),
    \texttt{dcache\_test} (multi-way fill, eviction, warm-cache hits,
    cold-miss-after-evict), \texttt{memory\_sections} (scratchpad heap
    write/read-back across the full address range). Each is a dedicated
    testbench (\texttt{tb/tb\_rv64i\_*.sv}) with its own multi-phase GPIO
    checkpoints (\texttt{GPIO\,=\,0x0N} per phase, \texttt{0x55} on final
    success), not the shared \texttt{tb\_rv64i\_instr.sv}.
  \item \textbf{cocotb ISS-scoreboard suite} (\texttt{cocotb/}, ported from
    \texttt{RV\_NoPipeline}'s): re-runs the same 59 programs
    instruction-by-instruction against a Python instruction-set simulator
    (\texttt{iss.py}), comparing architectural state every cycle rather
    than only the final GPIO byte. Since this variant has no directly
    pokeable instruction RAM, \texttt{tb\_flash\_wrap.sv} wraps
    \texttt{as\_top\_mem} with a behavioural QSPI NOR-Flash model (copied
    from \texttt{tb/tb\_rv64i\_instr.sv}) so a test program can be loaded
    by poking \texttt{flash\_mem\_s} directly -- bypassing JTAG, but
    exercising the real I-Cache/AXI4/QSPI path for every fetch.
  \item \textbf{AXI4 cache-error trap test:}
    \texttt{tb/tb\_cpupipefwd\_cachefault.sv} (xsim, standalone
    \texttt{CMakeLists.txt} in the same directory) verifies the
    \texttt{mcause}=1/5 trap path of Section~\ref{ss:axi4ErrCpuSeq}
    directly against \texttt{cc\_cpupipefwd.sv}, with a scripted
    \texttt{icpu\_if}/\texttt{dcpu\_if} response queue standing in for the
    cache (whose own \texttt{ic\_err}/\texttt{dc\_err} generation is
    separately unit-tested in \texttt{ip\_icache/tb/tb\_asICache.sv} and
    \texttt{ip\_dcache/tb/tb\_asDCache.sv}) -- this isolates the CPU's own
    fault-flag threading and \texttt{mcause}/\texttt{mepc}/\texttt{mtval}
    logic from the cache/AXI4 timing it is triggered by.
\end{itemize}

\subsubsection{Flush/Stall Priority Race (Fixed 2026-07-13)}
\label{subsubsec:flushStallRace}

During verification of the \texttt{ecall}/\texttt{ebreak} traps (a new
cycle-accurate cocotb ISS scoreboard, ported from \texttt{RV\_NoPipeline}
for this purpose), a pre-existing, previously-hidden pipeline bug was
found and confirmed by reproducing it against the unmodified RTL: the
\texttt{id\_ex} and \texttt{ex\_mem} pipeline registers only processed
\texttt{flush\_s}-driven squashing (branch/trap/\texttt{mret} redirect)
inside an \texttt{else if (!global\_stall\_s)} branch. When a redirect
landed on the exact same cycle as an ordinary one-cycle icache-hit lookup
stall, the flush was silently skipped: stale, wrong-path instructions
already latched in \texttt{id\_ex}/\texttt{ex\_mem} survived and were
committed once the stall cleared.

xsim's GPIO-only pass/fail check never caught this: the wrong path
happened to reach the same final output byte by coincidence, on every one
of the 68 tests then passing. It only surfaced once the ISS scoreboard
started comparing architectural state cycle-by-cycle rather than only the
final GPIO write.

Fix: \texttt{flush\_s} (and, for \texttt{ex\_mem}, \texttt{wb\_trap\_taken\_s}/
\texttt{wb\_mret\_s}) now takes priority over the stall gate in both
registers' clocking, matching how \texttt{if\_id}/\texttt{ibuf} already
handled the same situation. The general lesson -- \textbf{any squash
condition driven by a WB-stage or EX-stage event must never be nested
inside a stall-gated branch, since the two can coincide} -- was applied
again, by construction, when the AXI4 cache-error fault flags were added
later (Section~\ref{ss:axi4ErrCpuSeq}): \texttt{icache\_stall\_s}/
\texttt{dcache\_stall\_s} release on \texttt{ic\_err}/\texttt{dc\_err}
exactly like on \texttt{ic\_rvalid}/\texttt{dc\_rvalid}, so a fault is
never left waiting behind a stall condition that will never clear.

\section{System Memory Map}
\label{sec:sysmap}

Table~\ref{tab:sysmap} shows the complete address map of the \aschip{} system.
The address space is 64-bit.
Bit~32 of the address separates main memory (bit~32\,=\,0) from the peripheral
bus (bit~32\,=\,1); the peripheral bridge in \textbf{RV\_PipelineCacheFwd} uses
this bit to route accesses.
All peripheral registers are 64-bit wide and 8-byte aligned.
The column \textit{AW} gives the address-width parameter passed to the
peripheral's Wishbone slave interface (lower \textit{AW} bits of the full
address; the base address is always aligned to $2^{AW}$ bytes so the lower
\textit{AW} bits equal the register offset directly).

\section{Interrupt Map}
\label{sec:irqmap}

Table~\ref{tab:irqmap} shows how the peripheral interrupt sources map onto
the 8-bit \texttt{irq\_ext\_i} vector at the CPU boundary, for each chip
variant.
As detailed in Section~\ref{subsec:irqconcept}, \textbf{only bit~7 of
\texttt{irq\_ext\_i} is synchronised and evaluated by the CPU} (identically
in \texttt{as\_cpux} and \texttt{cc\_cpupipefwd}); bits~\texttt{[6:0]} are
declared \texttt{UNUSEDSIGNAL} in the CPU RTL and have no effect on program
flow, regardless of what is wired to them at the top level.

\begin{table}[H]
\caption{External Interrupt Map (\texttt{irq\_ext\_i})}
\label{tab:irqmap}
\centering
{\footnotesize
\begin{tabularx}{\textwidth}{|l |X |X |X|}
  \hline
  Bit & \textit{RV\_NoPipeline} & \textit{RV\_PipelineCacheFwd} & Consumed by CPU? \\
  \hline
  \hline
  7 & \texttt{icu\_irq\_s}: GPIO0 $\vert$ UART0, arbitrated by ICU0
    (\texttt{icu\_irq\_o}, Section~\ref{sec:icufunc01}); QSPI0 source tied
    to 0 (no QSPI0 in this variant) &
    \texttt{icu\_irq\_s}: GPIO0 $\vert$ QSPI0 $\vert$ UART0, arbitrated by
    ICU0 (\texttt{icu\_irq\_o}, Section~\ref{sec:icufunc01}) &
    \textbf{Yes} -- drives \texttt{mip.MEIP} \\
  \hline
  6\,--\,0 & tied to 0 & tied to 0 &
    \textbf{No} -- reserved (5 of ICU0's 8 source slots remain
    unwired, Table~\ref{tab:asIcuSrcAssign}) \\
  \hline
\end{tabularx}}
\end{table}

Both GPIO0 and UART0 (and, on \texttt{RV\_PipelineCacheFwd}, QSPI0) feed
ICU0 directly, not \texttt{irq\_ext\_i}; ICU0's own arbitrated output
\texttt{icu\_irq\_o} is the only signal driving bit~7. Firmware
determines the interrupt cause by reading \textbf{ICU0\_IRQID}
(Section~\ref{sec:icufunc01}) instead of polling each peripheral's own
\texttt{MIS} register -- this was an open item prior to ICU0's
introduction and is now resolved on both chip variants.
On \texttt{RV\_NoPipeline}, UART0's interrupt reaches the CPU for the
first time as a consequence of routing through ICU0 (see
Table~\ref{tab:asIcuSrcAssign}, ``Behavioural change on
\texttt{RV\_NoPipeline}''); previously it was wired to a bit the CPU never
read.
